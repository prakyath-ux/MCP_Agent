## Web — Frozen State

### Architecture

Three-pipeline design, all runnable independently or chained:

| Pipeline | Entry | What it does |
|---|---|---|
| **Extract Pipeline** | `qa.orchestrators.extract_pipeline` | One Chrome session: page_diagnostic → exhaustive_extract → validate_kb. Saves per-stage artifacts plus a synthesis JSON+TXT. |
| **Plan** | `qa.cli plan` | LLM reads L0 index, generates test cases. Pure reasoning, no browser. |
| **Execute** | `qa.cli execute` | Runs test cases via compound tools. Auto-invokes Plan if no test cases provided. |

Standalone orchestrators still callable directly:
- `qa.orchestrators.page_diagnostic`
- `qa.orchestrators.exhaustive_extract`
- `qa.orchestrators.validate_kb`

### Locator system

**Tier-aware XPath-first builder** in `qa.tools.web_tools.EXHAUSTIVE_SCAN_JS`:

| Tier | Strategy | Example |
|---|---|---|
| 1 | Single high-trust attribute | `//button[@data-testid='dropdown-button']` |
| 2 | Two attributes combined | `//input[@type='radio' and @name='X' and @value='Y']` |
| 3 | Three attributes (class-substring as third axis) | `//button[@role='button' and contains(@class,'card') and normalize-space()='X']` |
| 4 | Section scope (heading-anchored ancestor) | `//h2[='Bot Name']/ancestor::*[descendant::button[@aria-label='X']][1]/descendant::button[@aria-label='X']` |
| 5 | Positional within section scope | `(...scoped expr...)[2]` — flagged `disambiguation_failed=true` |
| 6 | Absolute DOM path | `/html/body[1]/div[2]/...` — flagged `disambiguation_failed=true` |

Inline uniqueness check: every candidate is verified via `document.evaluate` to match exactly 1 node before acceptance.

CSS locators saved as secondary (lower confidence) for tools that need them.

### Phase 1 — Dropdown options expansion

Extract-time pass that captures options for custom dropdowns whose list only renders on click. Single async JS round-trip per dropdown:
1. Snapshot pre-click visible elements
2. Click trigger + ArrowDown nudge
3. Wait 400 ms
4. Diff: newly-visible elements = popup contents
5. Three-pass option detection (standard markup → leaf-text in newly-visible → known popup containers)
6. Filter wrapper concatenation + placeholder leak
7. Escalating close: Escape → trigger toggle (Plan B) → documentElement click

**Verified:** TECU Branch (5 options), Forgenite Communication Tone (4 options).

### Phase 2 — Radio-group conditional discovery

For each native `<input type=radio>` group, click each option, re-scan, attribute newly-visible elements with `depends_on=[radio:<name>, option=<label>]`. Aria-radios skipped in v1.

Defense layers:
- **Layer 1:** Phase 1's escalating close runs after every dropdown expansion (prevents leftover popups bleeding into Phase 2 rescans).
- **Layer 2:** `_filter_popup_descendants` rejects new-element candidates whose XPath resolves inside a `[role=listbox/menu]` or popup-class ancestor.

**Verified:** Forgenite — 0 false positives across 3 radio groups (down from 7 in unfiltered v1).

### Tool layer — element_id first resolution

Three compound tools accept `element_id` as primary anchor; tool resolves the verified-unique locator from the injected KB:

| Tool | Signature |
|---|---|
| `fill_field_and_verify` | `(value, element_id="", css_selector="")` |
| `click_and_observe` | `(field_name="", css_selector="", element_id="")` |
| `test_dropdown` | `(css_selector="", select_option="", element_id="")` |

Refuse-on-ambiguous: any locator that matches >1 visible element returns `BLOCKED: AMBIGUOUS` instead of picking first match.

XPath auto-detection (leading `/` or `(/`) for the `css_selector` fallback so KB locators flow through cleanly.

`fill_field_and_verify` brackets each fill with console + network capture; new errors are attached to the result as authoritative bug evidence.

### KB Validator

`qa.orchestrators.validate_kb` — deterministic, no LLM. Takes a saved KB + live page, runs each L1 locator through `document.querySelector` / `document.evaluate`, attributes one of six verdicts per element:

- REACHABLE — unique + visible match
- HIDDEN — unique match, not currently visible
- DUPLICATE — every locator matches >1 node
- BROKEN — locators present, none match
- NO_LOCATORS — KB stored empty CSS+XPath
- LABEL_ONLY — only label fallback survived

Single browser round-trip; entire L1 list passed as JSON literal.

## Known Gaps (six)

Severity legend:
- **SOFT** — has a known workaround today; fix is incremental code (same pattern as Phase 1/2).
- **HARD** — no clean workaround; needs a new specialist module + careful state-management work.
- **HARD BLOCKER** — fundamentally impossible without app cooperation; document and move on.

| # | Gap | Severity | Concrete example |
|---|---|---|---|
| 1 | **Cascading dropdowns** | SOFT | TECU page 3 — `Select Employer` is empty until `Employment Status` is chosen |
| 2 | **Card-click reveals** | SOFT | Forgenite — `Voice Bot` button-styled card might reveal voice-config fields |
| 3 | **Checkbox-conditional fields** | SOFT | Toggle "Enable X" → reveals X-config fields |
| 4 | **Tabs / accordions** | HARD | Collapsed sections of long forms; tab clicks may navigate |
| 5 | **Modal contents (non-upload)** | HARD | Generic modals; close-button discovery varies wildly |
| 6 | **Iframe / Shadow DOM** | HARD (open) / **HARD BLOCKER** (closed shadow) | TinyMCE editors (open) vs. web components with closed shadow roots |

### Failure mode per gap

What you'd actually see in the UI when you hit each gap, plus today's workaround.

**1. Cascading dropdowns (SOFT)**
- *Symptom:* extract logs `OK status, but 0 options found (newly-visible elements: 0)`. KB stores dropdown with `options: []`. Plan emits `select_option="FIRST"` sentinel. Execute calls `test_dropdown`, popup opens empty, smart-fallback scans visible text and may grab a **wrong** on-page label → misleading PASS.
- *Workaround:* run extract with `--wait`, manually set the parent dropdown first, then press Resume. Child dropdown now has options.
- *Fix path:* `cascading_dropdown` specialist — detect parent (nearest preceding dropdown in same section), set parent's first non-placeholder option, retry child expansion.

**2. Card-click reveals (SOFT)**
- *Symptom:* button-styled cards (e.g., Voice Bot) captured as `type=button`. Plan generates `CLICK_AND_OBSERVE`. Execute clicks them. Any fields revealed by the card selection are **not** in the KB → never planned, never tested. Silent miss.
- *Workaround:* none clean. Manually pre-select the card, re-extract.
- *Fix path:* `card_toggle` specialist — detect button-styled-radio clusters (siblings sharing role/class), click each, DOM-diff for revealed fields, tag with `depends_on` (same machinery as Phase 2).

**3. Checkbox-conditional (SOFT)**
- *Symptom:* toggle hidden initially → conditional fields missed. Same silent-miss as #2.
- *Workaround:* manually toggle before extract.
- *Fix path:* `checkbox` specialist with toggle-and-rescan, mirror of Phase 2.

**4. Tabs / accordions (HARD)**
- *Symptom:* only the active tab/expanded section's content in KB. Other tabs/sections invisible. Extract has no idea they exist.
- *Workaround:* run extract per tab manually with `--wait`, save under different `screen_name`. The KB merges screens correctly.
- *Fix path:* tab/accordion specialist that clicks each, scans, restores. Risky — some "tabs" are actually navigation links (URL changes, page state lost).

**5. Modal contents non-upload (HARD)**
- *Symptom:* clicking a button opens a modal; modal contents not in KB; execute can't reach modal-internal fields.
- *Workaround:* open the modal manually with `--wait`, extract from there.
- *Fix path:* `modal` specialist — detect modal on click (look for new top-stacked overlay), scan contents, find close button (X / Cancel / Escape). Each app's close pattern is different; extensive recipe library needed.

**6. Iframe / Shadow DOM (HARD or HARD BLOCKER)**
- *Symptom:* form fields inside iframes/shadow roots not in scan results; diagnostic flags YELLOW (`same_origin_iframe`, `rich_text_editor_iframe`, `shadow_dom`). Execute attempts return ELEMENT_NOT_FOUND.
- *Workaround:* none. Diagnostic warns upfront so you know to skip these.
- *Fix path:*
  - **Same-origin iframes** — HARD (~½ day): traverse `iframe.contentDocument`, run scan recursively.
  - **Open shadow roots** — HARD: traverse `element.shadowRoot`, query inside.
  - **Closed shadow roots** — **HARD BLOCKER**. The browser API physically blocks access. Only fix is the app exposing a non-shadow alternative.

### Caveats on features that DO work

Easy to forget; document so future-you doesn't trust them blindly.

| Caveat | Why it matters |
|---|---|
| **Upload tool PASS is signal-based, not backend-verified.** Returns PASS when the uploaded filename appears somewhere on the page within 30s. | A PASS could mean frontend display update without a real upload. Verify true success by inspecting network for the upload's POST/PUT response (we don't auto-check this today). |
| **Tier-5 positional XPaths are fragile.** When extract can't disambiguate (e.g., 3 "More information" buttons in same section), L1 falls to `(...scoped expr...)[N]`. | Index breaks if the DOM order shifts (e.g., app reorders fields). Look for `disambiguation_failed=true` in the L0 `behavior` field; treat those locators as low-confidence. |
| **KB auto-merges screens by `app_name`.** Re-extracting with the same name replaces the matching screen, keeps others. | Stale screens accumulate (we saw `forgenite.json` end up with 5 mixed screens today). Use distinct `app_name` per app or run the cleanup one-liner periodically. |
| **Phase 2 covers `<input type=radio>` only.** Aria-radios (`role="radio"` on non-input elements) are skipped in v1. | Apps using aria-radios for conditional flows have those flows silently missed. Folds into gap #2 conceptually. |
| **`test_dropdown` smart-fallback can grab wrong text.** When `options=[]` AND `select_option="FIRST"` AND popup uses non-standard markup, the fallback scans visible page text. | Mitigated by Phase 1 capturing options pre-emptively. Risk returns whenever Phase 1 fails (cascading dropdowns being the main case). |
| **Diagnostic verdict is advisory, not gating.** GREEN/YELLOW/RED prints upfront; the pipeline runs regardless. | A RED page will still attempt extract + execute. User must read the diagnostic output to know what to expect. |
| **Plan blocklist is keyword-based.** Excludes buttons containing `save`, `continue`, `next`, `cancel`, etc. | Apps with non-English labels or unusual button text (e.g., "Apply changes", "Confirm and proceed") may slip through and trigger navigation/submit. |

### Cold-start troubleshooting

If you hit one of these symptoms after returning to the project:

1. **Extract pipeline finishes but synthesis panel doesn't render.** → Check `process.returncode == 0` AND the cmd contains `extract_pipeline`. The panel is gated by both.
2. **Resume button doesn't appear after Chrome opens.** → Look in the streaming output for `>>> Press Enter to start...` (literal string, with newline). If missing, the orchestrator's prompt isn't reaching stdout — verify the orchestrator uses `print(prompt, flush=True)` followed by bare `input()`, not `input(prompt)`.
3. **KB has 0 dropdowns when the page clearly has them.** → Check `classify()` in `EXHAUSTIVE_SCAN_JS`. Native `<select>` always works. `<button>` styled as dropdown needs ONE of: `data-testid` containing `dropdown`/`combobox`, OR `aria-haspopup="listbox|menu|true"`, OR label matching `^(select|choose|pick) X` + chevron/SVG descendant.
4. **`fill_field_and_verify` returns AMBIGUOUS.** → Element has no unique anchor on this page. Run `validate_kb` against the live page; check `disambiguation_failed=true` in the L0 `behavior` field. Tier-5/6 locators are inherently fragile.
5. **`validate_kb` shows 100% but execute fails.** → Likely KB drift across screens (see "KB auto-merges" caveat). Check `kb.screens` — are you validating against the right screen? Inspect `screen_name` in the validator output.
6. **Cascading dropdowns capture 0 options on TECU page 3.** → Expected (gap #1). Use `--wait`, manually set the parent dropdown, then continue. Or wait until `cascading_dropdown` specialist ships.
7. **A new Chrome window opens unexpectedly during a run.** → `_run_process` was cleared from `st.session_state` mid-run. Don't click "Run Test" while a run is active; use Kill Run + restart. The Run button is disabled while `running=True` as of `48bb582`.
8. **Phase 2 reports new conditional elements that look like popup contents.** → Check the streaming output for `[filter] dropped N popup-internal candidate(s)`. If 0 dropped but result still wrong, the popup container's class doesn't match our regex (`[role=listbox/menu]`, `[class*=popup/dropdown/menu]:not(button)`). Add the offending class to `_filter_popup_descendants` selector union.
9. **Phase 1 dropdown expansion captures wrong text (page labels instead of options).** → Popup uses non-standard markup AND new-element diff missed the right scope. Verify the popup's container is detected by the second-pass selectors in `expand_js`. May need a `[class*=YOUR_APP_POPUP_CLASS]` addition.
10. **Streamlit hangs on subprocess termination.** → Reader thread can hold open if subprocess closes stdout abnormally. The Kill Run button uses `_kill_process_tree` (SIGTERM → SIGKILL) which handles this. If hung, `pkill -9 -f extract_pipeline` from a terminal.

## Locked-in Architectural Decisions

1. **Compound tools handle escaping in Python.** LLM never hand-writes inline JS for routine fill/verify/click — bad escaping on a single value crashed entire runs in the past.
2. **`element_id` is the primary tool anchor.** Tools resolve locators from the injected KB. The LLM passes IDs from the test plan, not selectors.
3. **Refuse on ambiguous locators.** Tool returns `BLOCKED: AMBIGUOUS` rather than silently clicking the first match. Loud failure beats wrong-element pass.
4. **Diagnostic flags upfront.** Run starts with a YELLOW/RED report on known testability blockers; user knows the limits before spending tokens.
5. **KB validator gates trust.** A KB that doesn't validate against the live page is treated as low-confidence. `validate_kb` is deterministic, free, and fast.
6. **XPath is locator primary, CSS is fallback.** XPath supports text(), normalize-space(), parent-scope, positional indices — all needed for Tier 4/5.
7. **Mobile is untouched.** Any web change must guard with platform checks. Mobile pipelines are the production baseline.
