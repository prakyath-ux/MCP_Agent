## RECOMMENDATIONS

1. **Required field validation**
   - Ensure First Name, Last Name, Email ID, and Mobile Number:
     - Are marked `required` at the UI level.
     - Trigger validation on blur and/or input change.
     - Surface an inline helper/error text (e.g., “First Name is required”) bound to the field container.
   - If validation is deferred until “Save & Continue,” make sure inline errors appear when that action is attempted; currently no evidence of such behavior on simple blur/changes.

2. **Consistent validation framework**
   - Centralize required-field rules so all mandatory fields behave consistently.
   - Confirm whether client-side validation must exist or is server-only; if server-only, ensure immediate feedback on submit and clear mapping back to each field.

3. **Future test runs / deeper testing**
   - Re-run the full plan (TC5–TC20) once the guardrail/tool restriction is lifted:
     - Test format validation:
       - Email with valid/invalid formats (TC8, TC16, TC20).
       - Mobile number for length and numeric constraints (TC9, TC17).
     - Test name fields with punctuation and special characters (TC14, TC15, TC19).
     - Test Branch dropdown:
       - Required enforcement when empty on save (TC5).
       - Proper selection and retention (TC10).
       - Search/filter behavior (TC18).
     - Confirm Save & Continue / Save & Exit buttons exist, are enabled/disabled correctly, and do not allow progression with invalid or incomplete data.

4. **Accessibility considerations**
   - Ensure error messages are:
     - Programmatically associated with form controls via `aria-describedby` or equivalent.
     - Exposed with appropriate roles or live regions so screen readers announce them.
   - Required fields should have:
     - Clear visual indication (e.g., asterisk) and textual indication for screen readers (“required”).
   - Consider adding form-level summary on submit listing all fields with errors, in addition to inline messages.

5. **UX improvements**
   - If validation is intentionally on-submit only, still consider light inline cues on blur for critical fields to reduce user frustration.
   - Provide consistent error message wording across all required fields (e.g., “<Field> is required”).

Once required-field validation for empties is addressed, rerun TC1–TC4 to confirm fixes, then proceed with the remaining test cases for format and behavioral validation.
