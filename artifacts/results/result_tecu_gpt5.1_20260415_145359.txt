## RECOMMENDATIONS

1. **Required-field validation**
   - Implement and/or wire up required validation for:
     - First Name
     - Email ID
     - Mobile Number
     - Last Name  
   - Ensure errors appear:
     - On blur when the field is empty.
     - On submit/Save & Continue if required fields are not populated.
   - Confirm error messages match UX copy (e.g., “First Name is required”).

2. **Email validation**
   - Strengthen email format validation:
     - Reject clearly invalid local-parts like `MARISA!._@EXAMPLE.COM` if they are outside supported character set.
     - Display a clear inline error (e.g., “Enter a valid email address”) when format fails.
   - Re-verify plus-addressing remains supported (it worked for `+` case).

3. **Name fields and special-character handling**
   - Decide and document allowed character sets for First, Middle, and Last Name.
   - If special characters are **not** allowed:
     - Keep the user’s entered value in the field and show an explicit validation message instead of reverting to a previous value.
   - If certain punctuation is allowed (e.g., hyphen, apostrophe):
     - Adjust validation and transformation logic so valid characters are preserved and consistently uppercased, not silently discarded.

4. **Mobile number UX**
   - Current masking and truncation behavior for longer input (TC12) is acceptable per plan but should be:
     - Documented for business/UX.
     - Communicated near the field (hint text) so users understand only 7 local digits are stored.
   - After required validation is fixed, confirm error message text and placement.

5. **Branch dropdown automation / behavior**
   - For automated testing and accessibility:
     - Ensure the custom dropdown responds to keyboard interaction and native click events (not just framework-specific handlers).
     - Expose proper ARIA roles (`role="button"`, `role="listbox"`, `role="option"`) and support activation via keyboard.
   - For QA tooling specifically, enabling reliable programmatic interaction (or adding a hidden native `<select>` synced to the custom control) would make verification more robust.

6. **Accessibility and general UX**
   - Confirm all errors are:
     - Programmatically associated with their inputs via `aria-describedby`.
     - Announced by screen readers when they appear.
   - Ensure required fields are indicated both visually (e.g., `*`) and via accessible labels (e.g., `aria-required="true"`).
   - Avoid silently modifying or reverting user input without explicit feedback; always provide an inline message when changing or rejecting data.

7. **Areas for deeper testing**
   - Boundary testing:
     - Minimum/maximum lengths for name and email fields.
     - Non-numeric characters in mobile number.
   - Cross-field behavior on Save & Continue:
     - Once required validation is implemented, confirm the form blocks navigation and highlights all offending fields.
   - Multi-session behavior for Save & Exit:
     - Persistence of partially completed data including uploaded profile picture and branch selection.
