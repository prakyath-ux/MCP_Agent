## RECOMMENDATIONS

- **Enforce required validation consistently at field level**  
  All fields marked with `*` (First Name, Email ID, Mobile Number, Last Name) should surface a clear inline error when left empty and blurred, not only on full-form submission. This helps users correct issues earlier and supports assistive technologies.

- **Clarify and implement name field character rules**  
  - If digits and other non-letter characters are not allowed in First/Last Name, add pattern validation and surface an error (e.g. “Only letters allowed”) for inputs like `Lydia123` and `Walters123`.  
  - If such characters are acceptable (e.g. for suffixes or special cases), update requirements and any help text/placeholder to reflect that.

- **Tighten mobile number validation**  
  - Enforce minimum (and maximum) valid length based on the configured country format (+1868).  
  - Add a dedicated inline error for lengths that are too short or too long (e.g. “Enter a 7‑digit mobile number” or similar, depending on expected mask).  
  - Ensure the error is associated with the mobile input via `aria-describedby` for screen readers.

- **Align required behavior for Email ID when empty**  
  - Currently, invalid formats (e.g. `not-an-email`) correctly show “Please enter a valid email,” but fully empty values show no message.  
  - Introduce a separate required-message (e.g. “Email is required”) when the field is blank, so users understand that email is mandatory, not just format-validated.

- **Accessibility improvements**
  - Ensure all inline error messages are programmatically associated to their respective inputs (e.g. via `id`/`aria-describedby`) and exposed through the live region only when they change, to avoid confusion in screen readers.  
  - Confirm that required indicators (`*`) are also conveyed via `aria-required="true"` or similar, not just visually.  
  - For the Branch dropdown, keep using proper roles (`button` + `listbox`/`option`) and verify keyboard interaction (Up/Down/Enter/Escape) is robust.

- **Areas for deeper testing**
  - **Submit-level validation:** Since this run avoided clicking “Save & Continue” and “Save & Exit,” run a separate flow where those are clicked to verify that form-level validation catches all missing/invalid values before navigation.  
  - **Masking behavior for mobile number:** Explore how partial input, deletion, and paste operations interact with the mask and validation logic on different browsers and devices.  
  - **Branch dropdown search:** Validate filtering behavior and keyboard/screen-reader support for the embedded “Search…” box and option list.
