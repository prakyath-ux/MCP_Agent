## RECOMMENDATIONS

1. **Server- vs client-side validation alignment**
   - Implement or expose **client-side (inline) validation** for required fields (First Name, Email ID, Mobile Number, Last Name) so users get immediate feedback without relying on submission-time errors.
   - Ensure the error messages are visible and associated with the inputs via `aria-describedby` or similar for accessibility.

2. **Email validation**
   - Add basic syntactic email validation on blur (e.g., pattern, or JS validator) and show a clear error message for values like `"invalid-email"`.
   - Confirm behavior for edge-case valid emails (plus signs, subdomains, longer TLDs) in a future test pass.

3. **Mobile number behavior**
   - Review and correct the **masking logic**:
     - The field currently shows `"868-5551"` even after entering `"1234567890"`. Either:
       - the mask is incorrectly hard-coded, or
       - the test is only updating a display field while another hidden field actually holds the value.
   - Enforce correct **length and format validation**:
     - Reject too-short numbers such as `"8685551"` or display a clear error.
     - Ensure the visible value accurately reflects the entered digits (or the canonical stored value).
   - Clarify how the country code (`+1868`) and local number are combined and validated.

4. **Branch dropdown**
   - Ensure that after option selection:
     - The trigger button text updates to the selected branch label (e.g., `200 - TECU - COUVA BRANCH`).
     - The label is rendered as accessible button text (not only in a nested, visually-hidden element) so automated tests and assistive technologies can detect it.
   - Verify that there is clear inline validation if the user attempts to proceed without choosing a branch (likely tested during a navigation-step test pass).

5. **Required-field UX**
   - For all required fields:
     - Display a consistent, localized error message (e.g., “First Name is required”) when left blank and blurred.
     - Optional fields (like Middle Name) should remain error-free when empty; current behavior is correct.

6. **Accessibility considerations**
   - Confirm error messages use semantic indicators (`role="alert"`, `aria-live`) so screen readers announce them.
   - Ensure each input has an accessible name and the required status is announced (e.g., `aria-required="true"` or visible “*” in the label).
   - Verify the custom Branch dropdown complies with ARIA combobox/listbox patterns (focus management, keyboard navigation, `role="option"`, `aria-selected`, etc.).

7. **Areas for deeper testing in a follow-up round**
   - End-to-end submission to see if server-side validation compensates for missing inline checks, and whether it returns field-level errors.
   - Boundary tests:
     - Maximum permissible lengths for names and email.
     - Edge-case characters (accents, non-Latin characters).
     - Different valid/invalid phone formats including international cases (if supported).
   - Cross-browser checks for the custom masking and dropdown behavior to ensure consistent UX.
